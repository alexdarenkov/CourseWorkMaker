# AGENTS.md — CourseWorkMaker

Общие инструкции для всех AI-агентов, работающих с репозиторием.
Команды и инварианты редактируются здесь; требования к продукту — в docs/specs/.

## Проект

CourseWorkMaker (md2docx) — онлайн-редактор Markdown с живым постраничным превью «как в Word» и серверной конвертацией в DOCX по **ГОСТ 7.32-2017**. Первая публичная версия — редактор и экспорт без ИИ-агента. Документация и комментарии в коде — на русском. Свод ГОСТ, методички и текущего кода — `docs/reference/formatting-rules.md`; выбранные правила конвертера — в `docs/specs/`.

## Где лежит истина

Контракты поведения — **[каталог SDD](docs/README.md)** и `docs/specs/`.
Диалект — `markdown-dialect.md`, оформление — `formatting.md`, страницы —
`pagination.md`, работа с документом — `product.md`, интерфейс — `ui-ux.md`, API — `api.md`.
Трассировка — `docs/specs/verification.md`. Общие контракты приняты ранее;
подробные правила предложены для правок владельца, не автоматически приняты.

Устройство — `docs/architecture/`, причины выбора — `docs/decisions/`.
Этот файл хранит команды и инварианты разработки. Изменение поведения обновляет
спецификацию, код и тесты вместе; значимый архитектурный выбор дополнительно ADR.
Результаты конкретных прогонов — в PR/CI, каталоги audit/changes не используются.
Требования называются по смыслу; ссылки ведут на файл и раздел спецификации.
Исторические метки в существующих тестах не требуют переименования тестов.
Не искать удалённый PDF в корне. Источники и их различия описаны в
`docs/reference/formatting-rules.md`. Свод не делает все пункты автоматически принятыми; неясное правило
не выводить из кода. В документации писать просто, без лишних терминов.

## Главные правила

1. Меняя поведение — обновляй соответствующую спецификацию и тесты. Правь `AGENTS.md` в том же изменении, если меняется
   инвариант или устройство, описанное там.
2. Превью и DOCX — два параллельных рендера: правки диалекта/оформления
   вносятся на ОБЕ стороны (`frontend/src/lib/` ↔ `services/backend/app/convert/`)
   с тестами обеих сторон.
3. Стиль кода: минимальные изменения, следуй стилю файла; комментарии
   и сообщения об ошибках — на русском.
4. Существующую логику тестов не менять — исправлять только поломки
   от изменения интерфейсов.
5. Секреты, токены и содержимое `.env` не выводить и не коммитить.
6. Деструктивные операции — только по явному разрешению пользователя.

## Ветки и выпуск версий

- **`develop` — основная ветка интеграции.** Новые фичи и исправления начинают
  от актуальной `develop` и вливают в неё через PR. Префикс `codex/` не использовать.
- **`mvp-core` — текущая рабочая ветка:** удаление ИИ-агента и исправления ядра
  идут здесь, отдельными осмысленными коммитами; итоговый PR — в `develop`.
- **`archive/ai-prototype`** сохраняет версию с ИИ и аудитом на `ec2fc07`.
  Архив не изменять и не сливать целиком обратно. Будущее возвращение ИИ —
  отдельная ветка от актуальной `develop`, с адаптацией нужных компонентов.
- **`main` — проверенные релизы**, выпускаемые из `develop` и отмеченные тегом.
- Проверки, недоступные в окружении, указывать явно. Первая версия считается
  проверенной только после реального прогона Chrome и Word/LibreOffice,
  восстановления ZIP и проверки сохранности текста/изображений.

## Команды

```bash
# Полный запуск
docker compose up --build          # фронт: http://localhost:3000, backend: :8000

# Режим разработки: бэкенд в докере, фронт с hot-reload
docker compose up backend
cd frontend && npm install && npm run dev   # http://localhost:5173, vite проксирует /api на :8000

# Сборка/тайпчек фронтенда (линтера и форматтера в проекте НЕТ — ни eslint, ни ruff/mypy;
# `tsc -b` внутри build — единственная статическая проверка, гоняй её перед коммитом)
cd frontend && npm run build       # tsc -b && vite build

# Тесты фронтенда (vitest + happy-dom + @testing-library) — в frontend/tests/,
# зеркало src/ (tests/lib, tests/components, tests/hooks, tests/pages). Связи со спеками — в verification.md.
cd frontend && npm run test
# один тест: npm run test -- -t "<название теста>"   # напр. -t "GL-9"
# один файл: npm run test -- tests/lib/paginate.test.ts

# Тесты бэкенда (монолит; гоняются в docker — локальный python может быть старым,
# а формулам нужен pandoc, который ставится только в образе)
cd services/backend
docker build -t cwm-backend . && docker run --rm -v "$PWD/tests:/srv/tests" cwm-backend python -m pytest tests -q
# один тест: ... python -m pytest tests -q -k <name>   # напр. -k test_gost или -k test_limits
```

Образ бэкенда копирует только `app/` — тесты подмонтированы томом, поэтому правки в `tests/` видны без пересборки, а правки в `app/` требуют `docker build`.

Тесты бэкенда не требуют сети и БД. Тесты внешних изображений используют HTTP MockTransport.
CI проверяет наличие Pandoc и наличие `m:oMath` в DOCX. Локальный прогон без
Pandoc пропускает этот тест и не заменяет проверку production image.

## Архитектура

**Бэкенд — один FastAPI-процесс** (`services/backend/Dockerfile`, pandoc из apt). `app/main.py` подключает один роутер `app/convert` (`POST /api/convert/docx`, публичный). Бывшие Java-сервисы, gateway и отдельные converter/ai удалены (ADR-0010); аккаунты, JWT и PostgreSQL удалены (ADR-0012).

- **БД нет.** Серверного хранения документов нет: документ живёт в localStorage браузера, импорт существующих архивов — `.zip` (`lib/docArchive.ts` / `lib/docImport.ts`). Не добавляй серверное хранение документов без ADR.

**Фронтенд — React + Vite**, роуты в `src/App.tsx`: `/` (HomePage), `/editor`.

- **Дизайн интерфейса:** тема — `src/styles/tokens.css`, общие стили — `src/styles/components.css`, React-компоненты — `src/components/ui.tsx`. Повторяющиеся кнопки, поля и окна используют этот набор. Шрифт редактора задаётся `--font-mono` через общий `EDITOR_FONT` для textarea, подсветки и измерителя прокрутки. Шрифты документа ГОСТ от темы не зависят. Оболочка актуального TEXTURN — `src/styles/texturn.css`, декоративный ASCII-фон на canvas — `AsciiBackdrop.tsx`; размеры листов и метрики редактора от неё не зависят. Инструкция — `docs/architecture/design-system.md`, каталог компонентов — `/ui-test.html` только на dev-сервере.

- **`EditorPage.tsx` — владелец состояния** (`md`, `settings`); вся механика вынесена в хуки: `usePagination` (дебаунс 180 мс, перезапуск по готовности mermaid/картинок), `useDocPersistence` (localStorage, дебаунс 700 мс), `useScrollSync`, `useCaretMarker`, `useZoom`, `useToast`.
- **Синхронная прокрутка и маркер каретки** — отдельная подсистема (~950 строк) поверх пагинации. Общая «валюта» обеих панелей — ДРОБНЫЙ номер строки markdown: `lib/scrollSync.ts` переводит `scrollTop` редактора в строку и строку — в смещение по ленте страниц, `lib/caretMap.ts` + `lib/caretLocate.ts` уточняют позицию до символа внутри блока, чтобы построить Range в отрендеренном превью. Сгенерированные страницы помечены `Page.generated`; синхронизация исключает их высоту и зазоры из интерполяции и притяжения к краям (`scrollSync.ts`). При их просмотре редактор остаётся на месте; пересчёт сохраняет позицию ведущей панели, для титульника/содержания — индекс страницы внутри раздела и относительное смещение ([Синхронная прокрутка](docs/specs/core.md#синхронная-прокрутка), ADR-0011). Промежуточные точки — линейная интерполяция между якорями (`Anchor` в `paginate.ts`, ставятся по началам блоков). **Правя расстановку якорей в `paginate.ts`, чини и прокрутку** — она разъезжается молча, тестами в happy-dom это не ловится. Арифметика живёт в `lib/`, DOM трогают только хуки; тесты — `tests/lib/scrollSync.test.ts`, `caretMap.test.ts`, `caretLocate.test.ts`.
- **Геометрия ленты превью — только в `lib/pageGeometry.ts`** (размер листа, поля, зазор), высота строки — только `LINE_HEIGHT`/`LINE_HEIGHT_CODE`/`LINE_HEIGHT_SINGLE` в `gostRender.ts`. Их импортируют вёрстка (`PreviewPane`), авто-зум (`useZoom`), прокрутка (`scrollSync`), измеритель (`HOST_CSS` в `paginate.ts`) и дев-харнесс (`PAGE_CSS` в `previewTest.ts`) — константы не копируй, иначе панели молча разъедутся. Исключение, которое надо держать в голове: `PAGE_CONTENT_HEIGHT_PX` (971) в `paginate.ts` задан отдельным числом.
- **`lib/handoff.ts`** передаёт загружаемый File между страницами одноразово;
  File нельзя надёжно передавать через history state.
- **Картинки — через косвенность `asset:img-…`** (`lib/assets.ts`): в markdown только короткая ссылка, data-URL лежит в памяти + localStorage. Не вставляй base64 в текст документа.
- **Ключи localStorage:** `md2docx:v1` (md + settings), `md2docx:assets:v1` (картинки). Токена и пользователя нет — запросы к API анонимные (`api/client.ts`).

Перенос длинных формул выполняется в `frontend/src/lib/mathWrap.ts` внутри
скрытого измерительного DOM-хоста пагинации. Модуль использует только границы
`.base`, созданные KaTeX, и добавляет визуальные копии знаков с
`data-math-repeat`; `caretLocate.ts` пропускает эти копии при поиске каретки.

## Хранение, backup и границы безопасности MVP

- Документ локален для browser profile; аккаунтов и серверного хранения нет.
- `savePersisted` возвращает boolean. Постоянного статуса сохранения нет;
  при ошибке — уведомление и метка «Не сохранено · Повторить» в превью. Кнопка ZIP убрана;
  debounce записывается также при уходе из редактора/закрытии вкладки. При
  неудачной записи черновик остаётся в памяти для SPA-навигации, закрытие вкладки
  запрашивает подтверждение браузера. `loadPersisted` читает дисковую копию,
  `loadEditorDraft` предпочитает несохранённый черновик. Настройки валидируются
  отдельно: повреждение настроек не теряет текст.
- Ассеты добавляются атомарно: сначала localStorage, потом память. При квоте
  вставка отклоняется. Ассеты не удаляются автосохранением: они нужны для Undo.
  Это увеличивает расход localStorage; дальнейший GC должен учитывать историю.
- Модуль ZIP сохранён с тестами, экспорт не показан в UI; импорт доступен.
  ZIP v1: `document.md`, `document.json` (version/settings/images), `images/…`.
  При импорте ассеты получают новые ключи. Backup восстанавливает настройки и
  логотип; обычные `.md/.zip` по-прежнему импортируются. Внешние HTTP-картинки
  ZIP не скачивает — для автономной копии вставлять локальные файлы.
- ZIP: до 32 МиБ сжатых/распакованных данных и 512 записей; известные настройки
  проверяются по типам/диапазонам. Асинхронная распаковка через fflate с фильтром
  размера до распаковки. Markdown — до 2 млн символов, отдельный файл — до 8 МиБ.
- Backend: body до 32 МиБ до JSON-декодирования, до 256 ассетов суммарно 24 МиБ
  base64, 2 конвертации одновременно на процесс (переполнение → 429).
  В compose backend ограничен 1 ГиБ памяти, 2 CPU и 128 процессами, без capabilities.
- Внешние изображения: только HTTP(S), порты 80/443; все DNS-ответы должны быть
  публичными. HTTP-клиент соединяется с проверенным IP, исходный Host и SNI
  сохраняются; redirects и environment proxies запрещены. Поток ограничен
  10 МиБ, на документ — до 16 уникальных внешних URL, с кэшем на одну конвертацию.
- При вставке SVG/WebP/GIF нормализуются в PNG для совместимости DOCX.
  Недопустимые XML-символы в Markdown и титульнике отклоняются валидацией запроса.
- Обычные изображения и логотипы используют 96 px/in, как CSS-превью,
  независимо от metadata DPI. Только растр Mermaid учитывает DPI масштаба.
- Mermaid работает в `strict`; выполнение Python-кода и все `/api/ai/*` удалены.
- Конвертер публичный: nginx ограничивает экспорт до 6 запросов/минуту на IP
  (burst=3) и 2 одновременных запросов на IP. Production запускается отдельным
  `docker-compose.production.yml`: Caddy обеспечивает TLS, порты frontend/backend
  не публикуются. Доверенный IP Caddy согласован с `deploy/trusted-proxy.conf`.
  Инструкция — `docs/architecture/deployment.md`; smoke — `scripts/release_smoke.py`.
- Текущие regression tests находятся в frontend/tests и services/backend/tests.

## Главные инварианты

1. **Два параллельных рендера ГОСТ.** Превью (`markdown.ts` → `gostRender.ts` → `paginate.ts`) и DOCX (`convert/md_parser.py` → `convert/gost.py`) реализованы дважды и должны одинаково интерпретировать поддерживаемый диалект. Совпадение номеров страниц — критерий ручной приёмки на фиксированных документах; произвольная работа не имеет гарантии точного совпадения раскладки разных движков. Меняя диалект или оформление — правь ОБЕ стороны и тесты обеих сторон (`frontend/tests/lib/gostRender.test.ts` ↔ `services/backend/tests/convert/test_gost_layout.py`). Метрики строк (GL-2) меняются только парой. Листинги DOCX используют стиль `Code Block` (Courier New 12пт) для всего абзаца, включая переносы и пустые строки; `Unlisted Heading` сохраняет оформление реферата/содержания без выбора полем TOC по стилю Heading 1 ([Стили листингов и служебных заголовков](docs/specs/core.md#стили-листингов-и-служебных-заголовков)). Фикстура kalman-report существует в двух копиях (`frontend/src/fixtures/` = `services/backend/tests/convert/data/`) — менять только парой. Меняя пагинацию/рендер — прогони все сценарии дев-харнесса (`http://localhost:5173/preview-test.html?doc=toc|code|wide|mixed|report&page=N`, только dev-сервер) и сверь паритет страниц с DOCX бэкенда, открытым в Word/LibreOffice: число страниц и номера в содержании обязаны совпасть.
2. **Безопасность (SEC-1).** Аккаунтов нет, все маршруты публичны (ADR-0012). Не добавляй аутентификацию, БД или приватные маршруты без нового ADR; публичный маршрут обязан иметь лимиты размера и конкурентности, как `/api/convert/docx`.
3. **Overlay-подсветка редактора.** `<textarea>` и слой `<pre>` обязаны переносить строки одинаково: в стилях токенов только цвет/фон/border-radius; единственное исключение — рамка ```-блока и формулы $$…$$: `span` с `display:block`, фоном и скруглением без padding/margin/border, перевод строки после блока лежит внутри рамки (`lib/highlight.ts` + `components/EditorPane.tsx`) — любой отступ, шрифт или межбуквенный интервал в токене разъедет слои. Визуальная проверка — дев-харнесс `http://localhost:5173/highlight-test.html`.

## Границы тестов

Юнит-тесты фронта гоняются в happy-dom и **не измеряют реальную раскладку** (`offsetHeight` там не считается) — они проверяют разметку и правила рендера, но не то, где реально ляжет разрыв страницы. Пагинация верифицируется только дев-харнессом в настоящем Chrome + сверкой с DOCX. Тестам бэкенда БД не нужна.

Дев-харнессы — отдельные vite-страницы, а не роуты приложения: `frontend/preview-test.html` + `src/previewTest.ts` (ленты страниц по сценариям `?doc=…&page=N`) и `frontend/highlight-test.html` + `src/highlightTest.ts` (слои подсветки). Живут только на dev-сервере (`npm run dev`), в прод-сборку не идут.

Когда пишешь тесты фронта, помни про `tests/setup.ts`: в vitest 4 + happy-dom рабочего `localStorage` нет — там подменён общий in-memory Storage (чистится перед каждым тестом), а автоочистка RTL включена вручную через `afterEach(cleanup)`. Тест, ожидающий настоящий Storage или auto-cleanup от globals, поведёт себя не так, как кажется.

## Гочи деплоя

`docker compose restart` **не** перечитывает `.env` — нужен `docker compose up -d <service>`; docker-сборка иногда тихо не обновляет образ (кэш) — после деплоя сверяй артефакт в контейнере (backend: grep правки в `app/convert/gost.py`; frontend: имя бандла `index-<hash>.js` в `dist/` vs контейнер).
