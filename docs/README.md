# Документация проекта (SDD)

Проект ведётся по spec-driven development: поведение продукта описано в спеках,
код следует за спекой, а не наоборот.

## Структура

```
docs/
  specs/         — спеки: источник истины о поведении («ЧТО делает продукт»)
  decisions/     — ADR: «ПОЧЕМУ решили именно так» (история решений, не редактируется задним числом)
  architecture/  — «КАК система устроена» (as-is): обзор, API, схемы потоков (flows/)
  audit/         — конспекты изучения кода и подозрения на баги (рабочие заметки)
```

Разделение ролей документов:
- **Спека** отвечает «что должно происходить» — по ней пишутся тесты.
- **Архитектура** отвечает «как оно устроено сейчас» — по ней ориентируются в коде.
- **ADR** отвечает «почему так, а не иначе» — по нему не повторяют отвергнутые пути.
- README.md в корне — витрина для людей; CLAUDE.md — инструкции агенту
  (инварианты + ссылки сюда); AGENTS.md — указатель для сторонних AI-инструментов.

## Главное правило

**Ни одного изменения поведения без диффа в спеке — в том же коммите.**
Коммит с изменением поведения содержит три вещи: дифф спеки, код, тесты.
Схемы в `architecture/` подчиняются тому же правилу: изменил поток —
обнови схему в том же коммите.

## Цикл работы

1. **Спека до кода.** Правишь `docs/specs/<область>.md`: слой «Зачем» (если
   мотивация неочевидна), требование, критерии приёмки (Gherkin — где голой
   формулировки мало). Спорное решение — параллельно ADR (`/adr <тема>`).
2. **Ревью спеки** — `/spec-review`: противоречия с другими спеками и кодом,
   недоопределённости. Ловить ошибку здесь дешевле, чем в коде.
3. **Реализация против спеки.** Каждый критерий → тест; ИМЯ ТЕСТА содержит
   ID пункта (`MD-11`, `PAG-8`) — трассировка становится механической.
   Правила рендера реализуются и тестируются на ОБЕИХ сторонах
   (`gostRender.test.ts` ↔ `test_gost_layout.py`).
4. **Сверка перед коммитом** — `/spec-audit`: дифф кода ↔ дифф спеки ↔ тесты.

## Формат спеки

Шаблон — `specs/_TEMPLATE.md`. Кратко:

- Один файл = одна область поведения; пункты с ID `ПРЕФИКС-N`.
- ID никогда не переиспользуются; отменённый пункт не удаляется,
  а помечается «отменён (ADR-NNNN)».
- Слои пункта (сверху вниз): «Зачем» (бизнес) → требование (тех.) →
  критерии приёмки (Gherkin) → ссылки на реализацию/тесты/ADR.
  «Зачем» и Gherkin — по необходимости; пустой слой хуже отсутствующего.
- Статусы: `as-built` (выписан из существующего кода) → `принят` (согласован,
  ждёт реализации) → `реализован` | `отменён (ADR-NNNN)`.
- Для новых фич слои появляются по порядку: «Зачем» + Gherkin со статусом
  «принят» → ревью → реализация → ссылки на код/тесты и статус «реализован».

## Формат ADR

- Сквозная нумерация `0001, 0002, …`; имя файла `NNNN-краткий-слаг-латиницей.md`.
- Задним числом не редактируются. Передумали — новый ADR со ссылкой
  «заменяет ADR-NNNN», у старого статус «заменён ADR-MMMM».
- Разделы: Контекст → Решение → Альтернативы (и почему отвергнуты) → Последствия.

## Схемы

- Формат — mermaid прямо в md (GitHub/IDE рендерят нативно, диффы читаемы).
- Схем мало и только несущие: ключевые потоки в `architecture/flows/`,
  карта системы в `architecture/overview.md`. «По диаграмме на класс» — нет.
- Устаревшая схема вреднее отсутствующей — потому на схемы распространяется
  главное правило.

## Как менять и писать дальше: примеры

### Пример 1 — изменить существующее правило

Сценарий: вуз потребовал номера источников БЕЗ точки (сейчас с точкой, MD-11).

1. `/adr номера источников без точки` → `decisions/0004-….md`
   (контекст: требование изменилось; заменяет ADR-0003 — в нём проставить статус).
2. В `specs/markdown-dialect.md` правишь формулировку MD-11, ссылку меняешь
   на ADR-0004. ID остаётся MD-11 — меняется содержимое, а не номер.
3. Код на обеих сторонах (`gostRender.ts` ↔ `gost.py`) + тесты на обеих,
   с `MD-11` в именах.
4. `/spec-audit` → один коммит: ADR + спека + код + тесты.

### Пример 2 — новая возможность

Сценарий: поддержать сноски `[^1]` в диалекте.

1. В `specs/markdown-dialect.md` добавляешь `MD-17` со статусом **принят**:
   «Зачем», синтаксис, Gherkin-критерии с граничными случаями (сноска без
   определения? две ссылки на одну сноску? сноска в таблице?).
2. `/spec-review` — дыры и противоречия до начала кода.
3. Реализация: `markdown.ts` ↔ `md_parser.py` (парсинг), `gostRender.ts` ↔
   `gost.py` (рендер), тесты по каждому критерию.
4. Статус MD-17 → **реализован**, `/spec-audit`, коммит.

### Пример 3 — as-built спека из изучения кода

Разобрал модуль → конспект в `audit/<модуль>.md` (по шаблону) → правила
выжимаются в спеку со статусом `as-built`, потоки — схемой в
`architecture/flows/` → подозрения на баги остаются в audit-заметке
и превращаются в задачи.

### Пример 4 — нашёл расхождение кода со спекой

Это баг либо кода, либо спеки. Решаешь, что истинно; если истинен код —
правишь спеку (и ADR, если было осознанное решение); если спека — чинишь код.
Молча «подгонять» спеку под код без разбирательства нельзя — теряется смысл SDD.

инкрементально: первое изменение области = сверка её покрытия
(`/spec-audit`).
